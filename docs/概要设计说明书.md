## 1. 引言

### 1.1 编写目的

本文档是 AlphaMind 股票多 Agent 分析系统的概要设计说明书，旨在：

- 描述系统的整体架构和各模块的划分方式
- 明确模块间的调用关系与数据流转路径
- 阐述核心流程的设计思路与技术选型依据
- 为详细设计、开发实施、测试验证提供指导性规范

### 1.2 项目范围

AlphaMind 是一套面向个人投资者的智能股票分析系统，核心功能包括：

- **多 Agent 协作分析**：多个专业 AI Agent 依序完成行情、技术、舆情、投资组合四个维度的分析
- **辩论式研判**：多头、空头、中立三方持仓展开辩论，由仲裁官综合裁决
- **AI 对话助手**：支持 @mention 指定 Agent 进行深度问答
- **自选股管理**：收藏、监控目标股票
- **历史记录查询**：保留最近 50 次完整分析报告

## 2. 系统概述

### 2.1 业务背景

股票投资决策需要综合考量多维度信息：技术面（K 线形态、指标信号）、基本面（财务数据、行业动态）、情绪面（新闻舆情、资金流向）以及风险面（仓位管理、止损策略）。传统分析工具各司其职，缺乏整合视角。AlphaMind 通过多 Agent 协作，将多维分析自动化地整合为一份结构化报告，并支持与 AI 角色的深度对话，辅助投资者做出更理性的决策。

### 4.2 Agent 模块（`agent/`）

#### 4.2.1 BaseAgent 抽象基类

所有 Agent 继承 `BaseAgent`，获得以下共同能力：

| 能力 | 实现方式 |
|------|---------|
| 上下文共享 | `ThreadLocal<Map<String,Object>>` — 同一请求线程内的 Agent 间透明传递数据 |
| LLM 调用 | `llmCall(prompt)` 方法，内置三级降级链 |
| 模板降级 | 无 LLM 可用时自动返回预定义模板结果 |
| 提示词管理 | 从 `PromptRepository` 加载数据库中的动态提示词 |

```
BaseAgent
├── setContext(key, value)     // 写入 ThreadLocal
├── getContext(key)            // 读取 ThreadLocal
├── clearContext()             // 清理 ThreadLocal（必须在 finally 中调用）
├── llmCall(systemPrompt, userPrompt) // LLM 三级降级调用
└── analyze(report) [abstract] // 各子类实现具体分析逻辑
```

**ThreadLocal 生命周期规范**：

```
try {
    // 所有 Agent.analyze() 调用
    marketAgent.analyze(report);
    technicalAgent.analyze(report);
    ...
} finally {
    // 强制清理，防止线程池复用导致数据泄漏
    marketAgent.clearContext();
    technicalAgent.clearContext();
    ...
}
```

#### 4.2.2 Agent 职责列表

| Agent | 阶段 | 核心职责 | 输出字段 |
|-------|------|---------|---------|
| `MarketAgent` | Stage 1 | 获取实时行情、历史 K 线、基本面数据 | `report.marketData` |
| `TechnicalAgent` | Stage 2 | 计算 MACD/RSI/KDJ/Bollinger，识别形态 | `report.technicalIndicators` |
| `SentimentAgent` | Stage 3 | 分析新闻舆情、资金流向、情绪指数 | `report.sentimentData` |
| `PortfolioAgent` | Stage 4 | 综合评分，生成交易信号，提供风控建议 | `report.tradeSignal` |
| `BullAgent` | Debate 1 | 从多头视角论证看涨理由 | `report.debateViews[BULL]` |
| `BearAgent` | Debate 2 | 从空头视角论证看跌理由 | `report.debateViews[BEAR]` |
| `NeutralAgent` | Debate 3 | 客观评估，提供平衡观点 | `report.debateViews[NEUTRAL]` |
| `ArbitratorAgent` | Debate 4 | 综合三方观点，给出最终裁决 | `report.judgment` |

#### 4.2.3 LLM 降级链

```
Agent.llmCall(prompt)
    │
    ├─► LlmManager.call(prompt)
    │       │
    │       ├─► 遍历已注册模型列表（按优先级）
    │       │       │
    │       │       ├─ 检查熔断器状态 (CLOSED/OPEN/HALF_OPEN)
    │       │       ├─ OPEN → 跳过此模型
    │       │       ├─ CLOSED/HALF_OPEN → 调用 ChatModel
    │       │       │     ├─ 成功 → 重置失败计数，返回结果
    │       │       │     └─ 失败 → 累加失败计数，触发熔断阈值(3次)后开启OPEN
    │       │       │
    │       │       └─ 所有模型均失败/熔断 → 返回 null
    │       │
    └─ null → 使用 ChatClient 单模型直接调用
                  │
                  └─ 失败 → 返回模板文本（降级最低保障）
```

熔断器参数（`LlmManager`）：
- `FAILURE_THRESHOLD = 3`：连续失败 3 次触发熔断
- `OPEN_DURATION_MS = 30,000ms`：熔断冷却期 30 秒
- 冷却后进入 HALF_OPEN 状态，允许 1 次试探调用

### 4.3 Service 编排层（`service/`）

#### 4.3.1 PipelineOrchestrator

负责编排 Pipeline + Debate 两种分析模式的完整流程。

**核心方法签名**：

```java
public AnalysisReportDTO execute(
    String stockCode,
    StrategyType strategy,
    AnalysisMode mode,
    Consumer<SSEEvent> eventConsumer  // SSE 推送回调，同步模式传 null
)
```

**执行步骤**：

1. 初始化 `AnalysisReportDTO`，填充股票代码、策略类型
2. 从 `VectorMemoryService` 召回历史语义摘要（可选）
3. 顺序调用 4 个 Pipeline Agent，每阶段完成后推送 SSE `stage` 事件
4. 若模式为 DEBATE，委托 `DebateOrchestrator.runDebate()` 执行辩论
5. 将最终报告存入 `VectorMemoryService`（可选）
6. `finally` 块中清理所有 Agent 的 ThreadLocal 上下文

#### 4.3.2 DebateOrchestrator

按固定顺序执行辩论：`BullAgent → BearAgent → NeutralAgent → ArbitratorAgent`

**设计约束**：采用顺序（非并行）执行，原因是：单例 Agent 共享 `ThreadLocal` 上下文，并发调用会导致数据竞争。

#### 4.3.3 LlmManager

详见 4.2.3。提供 `call(prompt)`、`callWithModel(modelName, prompt)`、`reset(modelName)` 等管理接口。

#### 4.3.4 MemoryService

三层记忆架构：

| 层次 | 存储 | Key 模式 | TTL | 用途 |
|------|------|---------|-----|------|
| 短期 | Redis List → `ConcurrentHashMap`（降级） | `alphamind:session:{sessionId}` | 24h | 会话对话历史 |
| 中期 | Redis List + PostgreSQL | `alphamind:history:{stockCode}` | 持久 | 股票分析历史 |
| 长期 | Redis Stack Vector Store | `alphamind:vec:` | 持久 | 语义历史召回 |
| 摘要缓存 | Redis String | `alphamind:summary:{sessionId}` | 30min | 上下文摘要 |

### 4.4 策略系统（`strategy/`）

#### 4.4.1 StrategyType 枚举

| 值 | 中文名 | 持仓比例 | 止损线 | 持有天数 | 置信阈值 | 默认模式 |
|----|--------|---------|--------|---------|---------|---------|
| `CONSERVATIVE` | 保守型 | 30% | 5% | 45 天 | 75% | DEBATE |
| `BALANCED` | 均衡型 | 50% | 7% | 30 天 | 65% | DEBATE |
| `AGGRESSIVE` | 激进型 | 80% | 10% | 15 天 | 55% | PIPELINE |

#### 4.4.2 AnalysisMode 与模式解析

`StrategyModeResolver` 按以下优先级解析最终模式：

```
优先级 1：URL 参数 mode=PIPELINE|DEBATE
    ↓（未提供）
优先级 2：URL 参数 enableDebate=true|false（历史兼容）
    ↓（未提供）
优先级 3：strategy.getDefaultMode()（由策略类型决定）
```

#### 4.4.3 StrategySignalPlanner 评分逻辑

综合评分 → 交易信号映射：

```
综合评分 ≥ 70  →  BUY
综合评分 50-70 →  HOLD
综合评分 < 50  →  SELL

修正规则：
  BUY 但 confidence < strategy.confidenceThreshold → 降级为 HOLD
```

useEffect(() => {

  es.addEventListener('message', onMessage);

## 6. 核心流程设计

### 6.1 分析流程 — Pipeline 模式

```
用户操作                 前端                     后端
─────────────────────────────────────────────────────────
选股 + 选策略 → startAnalysis()
                    │
                    ├─► GET /api/v1/analysis/stream
                    │   ?stockCode=600519
                    │   &strategy=balanced
                    │   &mode=PIPELINE
                    │
                    │◄── SSE连接建立
                    │
                    │◄── event: stage (MARKET - "行情数据采集中...")
                    │◄── event: message (agentType=MARKET, data={...})
                    │
                    │◄── event: stage (TECHNICAL - "技术指标计算中...")
                    │◄── event: message (agentType=TECHNICAL, data={...})
                    │
                    │◄── event: stage (SENTIMENT - "舆情数据分析中...")
                    │◄── event: message (agentType=SENTIMENT, data={...})
                    │
                    │◄── event: stage (PORTFOLIO - "投资建议生成中...")
                    │◄── event: message (agentType=PORTFOLIO, data={...})
                    │
                    │◄── event: result (ApiResponse<AnalysisReportDTO>)
                    │
                updateStore()
                renderReport()
```

### 6.2 分析流程 — Debate 模式

在 Pipeline 4 个阶段之后，额外追加辩论阶段：

```
(Pipeline 完成后继续...)
                    │
                    │◄── event: stage (DEBATE - "多头分析师正在生成看多观点...")
                    │◄── event: message (agentType=BULL, data={...})
                    │
                    │◄── event: stage (DEBATE - "空头分析师正在生成看空观点...")
                    │◄── event: message (agentType=BEAR, data={...})
                    │
                    │◄── event: stage (DEBATE - "中立分析师正在进行客观评估...")
                    │◄── event: message (agentType=NEUTRAL, data={...})
                    │
                    │◄── event: stage (DEBATE - "仲裁官正在综合各方观点做出最终裁决...")
                    │◄── event: message (agentType=ARBITRATOR, data={...})
                    │
                    │◄── event: result (包含 judgment 和 debateViews 的完整报告)
```

### 6.3 PipelineOrchestrator 内部流程

```
execute(stockCode, strategy, mode, eventConsumer)
│
├─ 创建 AnalysisReportDTO
├─ VectorMemoryService.recall(stockCode) → contextSummary（可选）
│
├─ [Stage 1] MarketAgent.analyze()
│       └─ emitStage("行情数据采集中...")
│       └─ emitData(MARKET, marketData)
│
├─ [Stage 2] TechnicalAgent.analyze()
│       └─ emitStage("技术指标计算中...")
│       └─ emitData(TECHNICAL, technicalIndicators)
│
├─ [Stage 3] SentimentAgent.analyze()
│       └─ emitStage("舆情数据分析中...")
│       └─ emitData(SENTIMENT, sentimentData)
│
├─ [Stage 4] PortfolioAgent.analyze()
│       └─ emitStage("投资建议生成中...")
│       └─ emitData(PORTFOLIO, tradeSignal)
│
├─ [Stage 5，仅 DEBATE 模式]
│       └─ DebateOrchestrator.runDebate()
│
├─ VectorMemoryService.store(report)（可选）
│
└─ finally: 清理所有 8 个 Agent 的 ThreadLocal 上下文
```

### 6.5 SSE 事件规范

#### 分析流事件类型

| 事件名 | 触发时机 | data 结构 |

## 9. 非功能性设计

### 9.1 性能设计

| 指标 | 目标值 | 设计手段 |
|------|--------|---------|
| SSE 首事件延迟 | < 3 秒 | 异步响应，阶段性推送，不等待全部完成 |
| Pipeline 总耗时 | < 60 秒 | 各 Agent 独立 LLM 调用，LLM 超时 120 秒上限 |
| 股票搜索响应 | < 500ms | PostgreSQL 索引 + Redis 缓存 |
| 前端首屏 TTI | < 2 秒 | Next.js SSR + 静态优化 |
| 并发分析请求 | 10+ | WebFlux 非阻塞 IO，HikariCP 连接池 |

**SSE 心跳机制**：每 30 秒发送空注释行（`: heartbeat`），防止网络设备/反向代理因超时断开长连接。

### 9.2 可用性设计

| 设计点 | 方案 |
|--------|------|
| LLM 不可用 | 三级降级链：LlmManager → 单 ChatClient → 模板输出；系统永不因 LLM 不可用而崩溃 |
| Redis 不可用 | `MemoryService` 自动降级到 `ConcurrentHashMap` 内存存储 |
| 向量库不可用 | `VectorMemoryService` 检测 Bean 是否注入，未注入时静默跳过历史召回 |
| 数据库不可用 | Dev 环境通过 `application-dev.yml` 关闭 JPA 自动配置，不影响本地开发 |
| 熔断保护 | LLM 熔断器防止持续调用失败的模型，30 秒冷却后自动恢复 |

### 9.3 可扩展性设计

| 维度 | 设计方案 |
|------|---------|
| 新增 Agent | 继承 `BaseAgent`，注入 Spring 容器，在 `PipelineOrchestrator` 中引用 |
| 新增 LLM | 添加对应 Spring AI Starter，`LlmManager.setAvailableModels()` 自动注册 |
| 新增策略类型 | 实现 `StrategyProfile` 接口，在 `StrategyRegistry` 注册 |
| 水平扩展后端 | 无状态 HTTP 处理；会话状态存于 Redis，支持多实例部署 |
| 前端新增页面 | Next.js App Router 新增路由目录，Zustand 新增 Store |

### 9.4 安全性设计

| 安全点 | 设计方案 |
|--------|---------|
| CORS | `CorsConfig` 严格限制允许的源，通过配置文件管理允许域名 |
| 输入验证 | Controller 层使用 `@Valid` + Bean Validation 注解进行边界校验 |
| SQL 注入 | 全量使用 JPA/Spring Data 参数化查询，无裸 SQL 拼接 |
| 股票代码校验 | `VectorMemoryService` 使用正则 `^[A-Za-z0-9]{4,8}$` 校验，防止路径注入 |
| API Key 安全 | 所有 LLM API Key 仅通过环境变量注入，不存入代码或数据库 |
| XSS 防护 | 前端输出经 React 框架自动转义，不使用 `dangerouslySetInnerHTML` |
| ThreadLocal 泄漏 | `finally` 块强制调用 `clearContext()`，防止线程池复用导致数据泄漏 |

## 11. 关键技术决策

### 11.1 为何选择 Spring WebFlux 而非 Spring MVC

**决策**：后端使用 WebFlux 响应式编程模型。

**理由**：SSE 推送天然适合响应式流（`Flux<ServerSentEvent>`）。WebFlux 使用少量线程处理大量并发 SSE 连接，在多个用户同时发起分析时 I/O 效率更高。LLM 调用是 I/O 密集型操作，非阻塞 I/O 避免线程阻塞。

### 11.2 为何选择 ThreadLocal 而非方法参数传递

**决策**：Agent 间共享状态使用 `ThreadLocal<Map<String,Object>>`。

**理由**：Pipeline 中每个 Agent 需要读取前序 Agent 写入的数据（如 TechnicalAgent 需要读取 MarketAgent 写入的 `marketData`）。将所有上下文作为参数逐层传递会导致方法签名臃肿，且不利于未来扩展新 Agent。ThreadLocal 提供了隐式上下文传递机制，代价是**必须在 finally 块中清理**，已通过 `PipelineOrchestrator` 中统一的清理逻辑保障。

### 11.3 为何选择顺序辩论而非并行

**决策**：`DebateOrchestrator` 中 BullAgent/BearAgent/NeutralAgent 顺序执行。

**理由**：三个辩论 Agent 是单例 Bean（`@Service`），共享 `ThreadLocal` 上下文。若并行调用会产生数据竞争。同时，ArbitratorAgent 需要三方完整观点才能裁决，存在串行依赖关系。后续如需并行，需将 Agent 改为原型作用域（`@Scope("prototype")`）。

### 11.4 为何使用内存 ArrayDeque 而非数据库存储分析历史

**决策**：最近 50 条分析历史使用内存 `ArrayDeque`，不持久化到数据库。

**理由**：当前历史功能的主要场景是"查看本次会话内的分析记录"，重启后丢失是可接受的。内存存储避免了数据库写压力，访问速度也更快。需要持久化时，`AnalysisReport` 实体和 `AnalysisReportRepository` 已预留，可平滑切换。

### 11.5 为何前端使用相对路径而非硬编码 URL

**决策**：所有前端 API 请求使用 `/api/v1/...` 相对路径。

**理由**：通过 `next.config.ts` 中的 `rewrites` 规则将请求代理到后端，避免了 CORS 问题，同时使前端在不同部署环境中无需修改代码（只需设置 `BACKEND_API_ORIGIN` 环境变量）。

### 11.6 为何 VectorMemoryService 使用可选注入

**决策**：`VectorStore` 使用 `@Autowired(required = false)` 注入。

**理由**：Redis Stack（向量功能）需要额外的 Redis 模块，并非所有部署环境都具备。通过可选注入，系统在无 Redis Stack 时仍能正常运行（仅失去语义历史召回功能），降低了部署门槛。
